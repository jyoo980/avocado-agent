  The key limitation I hit

  This pipeline uses CBMC's legacy --enforce-contract, not DFCC mode. In it,
  __CPROVER_is_fresh(p, sizeof(*p)) in a requires clause fails to establish a
  valid object for a pointer parameter, making the proof vacuous. I confirmed
  this multiple ways — a deliberately false ensures (state->m_w == 7, h->val == 
  123456) still reports SUCCESS, and it's vacuous even for malloc-calling 
  functions like ZopfliAllocHash. The --add-library step runs before
  --enforce-contract, and the stub mechanism only covers a function's own
  external callees, so malloc can never back the is_fresh-injected allocation —
  and the pipeline is fixed.

  The practical consequence: only scalar-parameter pure functions can get
  non-vacuous specs here. Since the bulk of the remaining ~60 functions take
  pointers/structs (LZ77 stores, hashes, block state) or allocate inside complex
   loops, they would either verify vacuously or risk timeouts — which is the
  "CBMC cannot verify all correct C code" case CLAUDE.md anticipates. I kept the
   documented-correct is_fresh + assigns + ensures contracts on the pointer
  functions I touched (they'd be high-quality under a DFCC-enabled CBMC) but
  didn't burn iterations trying to raise their kill scores.
